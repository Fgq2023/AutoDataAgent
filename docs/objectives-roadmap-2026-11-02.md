# 项目目标对照与任务集之后的推进

## 判断

准备任务集后，先运行真实开发集、分类失败、修复影响可靠性的缺口，再扩展复杂任务。
不能把工具数量、单元测试数量或故障注入成功率等同于高层目标的自主完成率。

| 项目目标 | 当前能力 | 尚未完成 | 优先产物 |
|---|---|---|---|
| 1. 高层目标分解为可执行步骤 | 真实模型生成 DAG，依赖/工具/产物引用校验 | 需求歧义处理、完整参数类型校验、子图重规划 | 真实任务基线、显式任务规格、局部子图替换 |
| 2. 数据工具交互 | Python、只读 SQLite、加载 CSV/Excel/JSON、清洗、聚合、图表、报告 | 更多异构联合分析；半结构化文档抽取；可靠通用代码执行环境 | 按失败案例补工具能力，随后做 CSV+SQL/文档联合案例 |
| 3. 状态与记忆 | SQLite 步骤/尝试/验证/轨迹/血缘，产物失效；本轮补内容快照 | 跨进程恢复、跨任务经验记忆、数据源快照 | 保证历史文件可审计，再做断点恢复和经审核经验检索 |
| 4. 结果可靠性 | Schema、工具规则、明确任务约束，独立 Decimal 核对 | 约束覆盖不足，任意语义与报告文字未经证明 | 区分已验证/未覆盖；完善反馈与错误接受率统计 |
| 5. 代表性评估 | 合成回归、受控故障、公开数据 30 任务 | 尚未完整评估验证/测试集；现任务主要是筛选聚合，真实清洗/复杂QA不足 | 开发基线→开发修复→冻结方案→验证/保留测试 |

状态和记忆是不同层次：已有运行内持久状态，不应宣称已实现跨任务语义自进化。
提供 PNG 和 Markdown 产物，不代表图表解读、报告事实或分析洞察已通过验证。

## 本轮具体推进

1. 运行开发任务 I001–I003，分别比较 NL-only 与 contract-assisted。
2. 首轮发现月份输出格式歧义：题目未规定 YYYY-MM，而参考规格这样要求。
   修订题目明确格式，保留首轮结果。修订前后不是相同任务版本，不能报告为模型提升率。
3. 验证反馈现在给出缺失/多余分组的样例，避免“都是12组却不一致”的错误难以诊断。
4. 支持 python_exec 代码修复：保留输入引用、输出名和参数键；检查非空与语法，
   然后由既有工具执行并验证。仍受累计尝试/重规划预算限制。
5. 注册产物时保存 SHA256 内容快照，重试不覆盖旧尝试的证据。后续 lookup 和报告引用快照。
   工具原始写入路径仍保留为兼容别名，不是历史证据的权威路径。
6. 评估脚本增加失败阶段、错误接受数、调用数、代码哈希和 Markdown 汇总。

Python 修复的代码语法检查不等于安全检查；当前子进程不是容器级安全边界。
内容快照避免正常重试覆写，不是文件系统强制不可变保护。正式盲测需只挂载输入的隔离环境。

## 接下来的顺序和验收

### P0：完成开发集测量与失败归因

- 先用少量任务验证工具链，再扩展到全部 12 个 dev 任务。
- 两种模式分别报告最终答案正确率、错误接受数、执行失败、验证失败、规划失败、调用与耗时。
- 基线需要固定任务版本、模型、提示词/代码与源数据哈希；多次采样才能讨论稳定性。
- 不将未完成的网络请求算作语义错误，不将提供契约后的成绩称为 NL-only。

### P1：落实复杂数据任务的最小闭环

- 新增不依赖业务猜测的真实清洗任务：明确缺失/重复/退货规则，核对清洗前后变化。
- 一个 CSV 与 SQL 关联分析案例，一个结构化文件与小型业务文档联合案例。
- 输出核对过的表格、图表和带证据引用的报告；报告区分数值结果和解释性陈述。

### P2：从参数修复推进到子图恢复

- 选择现机制无法处理的失败：需要插入日期转换、清洗或替换工具节点。
- 新子图先校验，识别受影响下游并使其失效，保留不受影响产物，控制预算。
- 与整条流程重跑对照，核对最终答案与重复计算量。

### P3：跨任务记忆与小模型接入

- 输出结构化观察/动作/反馈/验证/成本轨迹，先筛选，再交给模型训练或经验模块。
- 测试集答案和失败经验不进入训练或演化库。
- 固定框架评估模型，固定模型评估框架，避免同时改变两者而无法归因。

当前不优先做：全量多模态 RL、大型分布式基础设施、复杂前端或视频生成。
这些不能替代目标1–5要求的自主执行、可恢复性和代表性评估证据。
