# 任务级语义验证：年份与指标口径

## 实现与边界

首版新增独立于模型计划的 `customer_totals_year` 契约，
针对演示数据库 customers(id,name) 与 orders(customer_id,order_date,amount)。
输入是用户/开发者明确指定的数据源、年份和输出产物名，不从模型计划反推“正确答案”。
后续已增加通用 `tabular_aggregate`，见 `generic-task-contracts.md`；本文记录首版实现与实验。
示例配置见 `task-contracts.example.json`，相对数据源路径以配置文件目录为基准。

验证器以只读方式读取原始订单，按要求年份逐条计数并用 Decimal 累加金额，
核对客户集合、行数、列名、订单数及总额。金额允许 0.005 的舍入误差，不检查行排序。
同名客户按名字合并，语义与当前演示任务一致；并非适用于所有业务的客户身份定义。
不验证报告文字是否正确、图表像素、任意 SQL 意图或复杂业务规则。
完整扫描参考数据适用于当前小规模示例，尚未优化大表性能或缓存。

task checks 不受模型 Step.verify 开关控制。计划缺少约定输出会在执行前被拒绝；
步骤未生成约定产物时也会失败。契约失败归类 verify，失败产物失效，不能继续生成报告。
结构化反馈包括失败检查与预期年份/指标，进入已有的预算控制和参数修复流程。
SQL 修复只允许修改现有参数值，source 和输出名不可更改，查询需通过只读检查。
SQLite 连接现在也以 mode=ro 打开，避免只依赖关键词过滤。

## 真实模型对照结果

2026-10-30，OpenCode Go / deepseek-v4.1-flash。
证据：`outputs/semantic__172skeq/report.md`、`results.json`、各场景 calls.json 与 trace.json。
初始计划来自模板，故意注入错误；真实模型仅负责修复。

| 任务 | 原检查 | 契约验证，无模型修复 | 契约验证 + 真实模型修复 |
|---|---|---|---|
| 正常 2024 年总额 | 正确完成 | 正确完成 | 正确完成，0 次模型调用 |
| 错误过滤为 2025 年 | 错误接受 | 拦截，未生成最终报告 | 正确完成，1 次模型调用 |
| 错误使用 AVG 代替 SUM | 错误接受 | 拦截，未生成最终报告 | 正确完成，1 次模型调用 |

这是同一份演示数据上的两种故障、每组各一次运行；没有统计显著性或开放任务准确率结论。
模型输出通过契约后才接受，因此不能将“能执行”替代为“答案正确”。
失败尝试的状态与元数据保留；现有产物文件路径会复用，尚未实现每次尝试的不可变文件快照。

## 运行

```powershell
# 普通运行，启用明确任务契约
.\.venv\Scripts\python.exe -m agent "查询 orders.db 中 2024 年每个客户的总消费金额" --task-contracts docs/task-contracts.example.json

# 已设置 OPENAI_* 环境变量后，复现 3 种任务 x 3 组对照
.\.venv\Scripts\python.exe scripts/run_semantic_validation.py
```

没有指定契约时保留原行为。下一阶段需把任务要求表达扩展到通用指标与过滤条件，
并解决需求提取与独立验证之间的关系，而不是无限增加演示专用规则。
